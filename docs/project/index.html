What the model accounts for.

The work of computing tokens and the progress of accepting them are different quantities.

Follow the implementation
Propose
N-gram or fixed overhead, or a separately trained draft-model predictor. Draft weights and KV cache consume memory.
Verify
Charge for k + 1 computed tokens. Compare a shared-KV lower bound with a per-token upper bound; an interpolated mode is also available in the simulator.
Advance
Keep the accepted prefix plus one target token. Respect Sarathi’s token budget, request boundaries, and lookahead KV allocation.

The next question belongs on a GPU.

The repository includes a vLLM validation harness: replay matched workloads, calibrate acceptance from server counters, then compare measured and simulated latencies request by request.

No real GPU validation results are published here. Unit tests and a fake-server harness check behavior; they do not establish timing accuracy.

Read the bounds with the assumptions.

Scheduler scopeSpeculative decoding supports Sarathi with pipeline parallelism 1. Acceptance is an input, not a prediction.

Approximate costsVerify attention uses existing decode profiles. Short drafts and draft pass 1 are approximate; rejection-sampler overhead is omitted.

Profile and load limitsThe bundled profiles predate current vLLM kernels. The 6 requests/s baseline is overloaded, so ratios depend on run length.
